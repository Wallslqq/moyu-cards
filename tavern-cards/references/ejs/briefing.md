# EJS 需求守门与工件合同

> 本篇是 EJS 的**需求守门层**：先判断是否真的需要 EJS，需要时产出实现合同。合同确认后的语法、复杂度分级与实现完全走 `references/ejs/guide.md` 原链路（条目显隐 → 段落控制 → 动态文本）。

EJS 是由 ST-Prompt-Template 扩展在世界书文本中执行的模板。它可以按条件输出文本，也可以在作者明确需要时调用扩展提供的变量、角色卡、世界书或注入能力。设计阶段必须先确定「为什么需要动态处理」，再决定使用哪一项能力。

## 一、先选最简单的落点

- 永久稳定的设定：放入普通人物、世界书或创作规则条目，不使用 EJS。
- 只需关键词触发的设定：使用普通关键词世界书（🟢绿灯），不使用 EJS。
- 需要按当前状态选择不同文本、循环生成结构、读取扩展变量或进行动态注入：才进入 EJS，复杂度按 `references/ejs/guide.md` 分级判定。
- 只是为了把静态内容写得复杂：拒绝使用 EJS，避免给作者增加维护成本。

## 二、每份方案必须确认的事实

1. **唯一目的**：这份 EJS 在什么时候解决什么问题。
2. **执行位置**：挂在哪个世界书条目上运行；该条目的类型、part、depth 与发送顺序由创作规划中的条目定义决定（见 `references/conventions.md`），规划时确定。
3. **输入来源**：只列真实需要读取的变量路径（`stat_data.` 前缀，须在 schema.ts 中有定义）、当前消息、角色卡字段、世界书内容或扩展 API。未需要的能力不得加入。
4. **输出正文**：命中后究竟向模型发送什么；不命中时是空输出、默认文本还是其他行为。
5. **分支与覆盖**：条件必须互斥或明确优先级，并存在可解释的默认分支。
6. **副作用**：默认只读。只有作者明确要求修改变量、插入内容或调用其他能力时，方案才允许副作用，并必须写清触发条件和重复执行风险。
7. **失败边界**：缺失变量、错误类型、扩展 API 不存在或返回空值时如何安全退回。
8. **验收例子**：至少给出一个命中例子和一个不命中／回退例子，用于核对逻辑，不替作者虚构作品事实。

## 三、getvar 约定

与 `references/ejs/guide.md` 完全一致（两者同源 ST-Prompt-Template）：

- 读取 MVU 字段时使用大小写固定的 `getvar('stat_data.完整路径')`；路径必须逐字来自当前 MVU 文件。
- 第二参数 `{ defaults: 缺省值 }` 按失败边界决定是否提供，确保不会因变量未注册而抛 ReferenceError。
- 函数名只能是全小写 `getvar`；不得改写成 `getVar`，不得读取名为 `mvu` 的整段字符串，也不得发明 `getMvuData`、`getVariables` 等替代 API。
- 当前作品启用了 MVU 时，合同引用变量前先读取 `schema.ts` 核对路径存在；只有需求确实依赖变量时才能引用。

## 四、合同 → 条目规划字段映射

方案确认后，把合同落进 `创作规划.yaml` 的 `ejs.entries[]`（字段定义见 `references/requirements/planning-yaml.md`）：

| 合同项 | 规划落点 |
|--------|----------|
| 工件名称 | `entries[].name`（与条目名对应） |
| 唯一目的 | 所属条目的 `abstract` 摘要 |
| 复杂度落点 | `entries[].complexity`（条目显隐／段落控制／动态文本） |
| 输入来源与分支条件 | `entries[].condition`（或调色盘的 `stages[]`），内含 `getvar('stat_data.…', { defaults: … })` 表达式 |
| 执行位置 | 所属条目在 entryManifest 中的注册（`path`／`part`／depth 与排序，由条目类型决定） |
| 输出正文 | 所属条目的内容文件（实现阶段按 guide.md 写入 EJS 代码） |
| 默认与失败回退 | `condition` 中的 `{ defaults: … }` 与内容文件的回退分支 |
| 验收例子 | 留在对话与条目 abstract 备注中，供收尾一致性检查对照 |

实现阶段对照 `references/ejs/guide.md` 的分级处理：条目显隐用 `contents` 首片段 `@@if`；段落控制与动态文本编辑条目内容文件；所有 `<%` 与 `%>` 数量一致、控制结构在工件内闭合、不命中时按合同真正保持空输出（不泄漏阶段名、调试说明或技术错误）。

## 五、交谈方法

作者是新手时，用白话解释「模型会在什么时候看到什么」；不得用 API 名称堆砌答案。作者提出明显超出 ST-Prompt-Template 或 SillyTavern 运行边界的效果时，直接说明不能稳定实现，给出最接近的可行替代。

一次只问一个会改变结构的问题。已经从当前工作区确认的内容不重复追问。功能、输入、分支、回退和条目位置全部确定后，应主动告诉作者「方案已经足够生成成品」，不要求继续添加无用细节。

## 六、方案格式

最终仅输出：

```text
<EJS工件方案>
工件名称：
唯一目的：
运行时机与位置：
读取内容：
输出内容：
条件与优先级：
默认与失败回退：
允许的副作用：无／逐项写明
实现所需 API：只列已核实且本工件需要的能力
命中验收：
回退验收：
条目配置：所属条目与注册位置（type/part/depth）；概率 100；默认不递归
</EJS工件方案>
```

随后按第四节把合同写入 `创作规划.yaml` 的 `ejs` 段，并继续条目创作流程（`references/conventions.md`）。
</knowledge_ejs_briefing>
